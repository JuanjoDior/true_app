# Case review and publish — ODD

## Objective
Let Iván author cases locally in an installed Windows app and explicitly send a completed draft for review. The developer reviews from a separate device and approves it for the public web catalog without a code deploy per case. Supabase transports submitted snapshots and serves published cases; continuous cloud draft synchronization is out of scope. The public web host is undecided; GitHub Pages remains the current deployment until a separate delivery decision.

## Data model (implemented locally in CRP-01)
- `cases`: `slug` (pk), `payload jsonb` (the exact case object the app already reads from `cases.json`, stored raw to avoid lossy model round trips), `published_at`, `published_by`. Public read; write only by the reviewer.
- `drafts`: `id` (pk), `owner` (auth user), `payload jsonb` (`CaseDraft.toJson()`), `status` (`draft | in_review | returned | published`), `updated_at`. Read/write by owner while `draft`/`returned`; owner cannot edit while `in_review`; reviewer reads all `in_review` and changes status.
- `reviewers`: user ids allowed to approve (the developer). Approval = upsert into `cases` + set draft `published`, in one database function so it is atomic and enforced server-side.

## Decisions
- 2026-09-27 — Unpublishing: only the reviewer (developer) withdraws published cases, from the reviewer inbox; Iván has no unpublish action and asks by phone. RLS: delete on `cases` restricted to reviewers.
- 2026-09-27 — Free plan kept. A scheduled GitHub Actions workflow queries Supabase every few days (prevents the 7-day inactivity pause) and exports published cases and drafts as JSON. Backups go to a dedicated `backups` branch, never `main`, because every push to `main` redeploys Pages. Draft export needs the service-role key as a GitHub secret; never ship that key in the app.
- 2026-09-27 — `assets/data/cases.json` is removed after the CRP-02 seed is verified; no offline fallback, because a stale bundled catalog shown as real is worse than an explicit «no se pudieron cargar los casos» with retry. Tests and code that read the real asset must move to fixtures or the seed file in the same work unit.
- 2026-09-27 — Editing a published case always goes back through review: Iván edits the draft (status returns to `draft`), resends, and the published version stays live and unchanged until the reviewer approves the new one.
- 2026-09-27 — Sign-in is e-mail + password with accounts created by the developer, not invitations or magic links. Reason: without custom SMTP, Supabase's built-in mail only delivers to members of the project's organization team (2 messages/hour), so an invite or magic link would never reach Iván; magic links also only complete in the browser that asked for them. Consequences: open sign-up is disabled, minimum password length 12, no «forgot password» — the developer resets passwords from the dashboard. Custom SMTP (e.g. Brevo) can be added later if more authors join.
