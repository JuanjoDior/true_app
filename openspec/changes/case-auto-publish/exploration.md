## Exploration: case-auto-publish (working name — see naming note)

### Naming note
"case-auto-publish" overstates the likely scope. Nothing in this codebase can perform a real "auto-publish" (git commit + GitHub Pages deploy) from a static, backend-less Flutter Web app. The actual gap is narrower: eliminating hand-editing of `assets/data/cases.json` between "export" and "commit". Suggested alternative names: `case-export-catalog-merge`, `intake-catalog-handoff`, or `case-export-drop-in`. Kept `case-auto-publish` as the artifact key per orchestrator assignment.

### Current State

**Data flow today (verified against current source, not just the archived proposal):**
1. Editor fills the intake form (`IntakeWorkspaceScreen`, gated by a hardcoded shared passphrase `kIntakeSharedKey = 'archivo-ivan-2026'` in `intake_gate_screen.dart` — explicitly documented as "not real security", and it ships inside the same public deployed web bundle as the map, not a separate local-only tool).
2. `ExportCaseButton` (`lib/features/cases/presentation/intake/export_case_button.dart`) is enabled once `validateDraft(draft).isValid` (`draft_validator.dart`) — which only requires title, category, year, status, country, countryCode, regionOrCity, latitude, longitude. Chapters, photos, timeline, featuredRank/relevanceRank are NOT required to export.
3. Clicking it calls `encodeDraftAsCaseJson` (`case_exporter.dart:182`) which calls `draftToCaseJson` (`:100`), and copies **one JSON object** (a single case, NOT wrapped in an array) to the clipboard. The snackbar literally says: "JSON copiado. Pégalo en assets/data/cases.json".
4. The code's own top-of-file comment states this is deliberate: "Es el único puente entre el borrador local de Iván y el catálogo publicado: no hay backend ni CMS, así que el flujo es exportar, pegar en el asset y commitear." This matches `openspec/specs/case-editorial-chapters/spec.md`'s "Manual Publication Boundary" requirement (still in the current merged spec baseline), which explicitly forbids export from auto-updating the catalog.
5. `assets/data/cases.json` is a JSON **array**. `LocalCasesRepository.getCases()` (`lib/features/cases/data/local_cases_repository.dart`) loads it via `rootBundle.loadString` (a Flutter **asset**, bundled at build time) and parses it with `jsonDecode(...) as List<dynamic>` → `TrueCrimeCase.fromJson` per element. `CasesRepository` (the abstract interface) has exactly one method, `getCases()` — there is no write path in the data layer at all.
6. Because the exporter emits a single object but the target file is an array, a human must open `assets/data/cases.json`, find the right place, and manually splice the object into the array (comma/bracket placement) before saving and running `git commit`. **This splice-into-array step is the actual, concrete manual friction** — not a full-file replace, and not a schema mismatch.

**Round-trip fidelity (the crux of the user's complaint):** Compared `draftToCaseJson`'s emitted keys field-by-field against `TrueCrimeCase.fromJson`'s expected keys: id, slug, title, category, country, countryCode, regionOrCity, year, latitude, longitude, summary, tags, sources, status, victim, timeline, photos, chapters, featuredRank, relevanceRank — every field matches exactly, no unlisted transformation is needed. `test/case_exporter_test.dart` has an explicit test, "produces a case the app can actually load back", asserting `TrueCrimeCase.fromJson(draftToCaseJson(draft))` round-trips correctly, plus dedicated coverage for coordinate rounding, slug collision suffixing, chapter emission, photo/timeline/victim/tag carrying, and (new) a `group('featured and relevance ranks')` block. **Conclusion: there is zero hand-editing of field *values* required today — the only manual step is array insertion + save + commit.**

**Rendering pipeline is already fully wired once a case is in the array** (contradicts a stale code comment):
- Editorial chapters, public route `/#/casos/<slug>`, and the published-case directory are shipped (archived change `2026-08-15-case-publication-detail`; specs `case-editorial-chapters`, `case-publication-route`, `published-case-directory`, `expanded-case-dossier` are all in `openspec/specs/` as the current merged baseline).
- Photos: `case_dossier_content.dart:160-164` renders `_PhotoStrip` when `crimeCase.photos.isNotEmpty`. This directly contradicts the comment in `case_exporter.dart` ("Las fotos aún no se pintan en el expediente publicado") — that comment is stale; photos ARE rendered in the shared dossier presentation today.
- `featuredRank` (captured in intake since commit `faec1ee`) already drives `featuredCaseProvider` in `cases_providers.dart:190-200` — picks the case with the lowest `featuredRank` for the home "EN EL FOCO" featured slot.
- `relevanceRank` already drives `_compareByRelevance` in `case_search_service.dart:72-78` — used in search-result ordering.
- The published-case directory (`published-case-directory` spec, Requirement "Complete Deterministic Directory Ordering") explicitly and intentionally excludes `featuredRank`/`relevanceRank` from directory ordering (year desc → title asc → slug asc only) — this is spec'd, not a gap.
- So: once a case object is correctly inside the `assets/data/cases.json` array, it renders completely everywhere (map, directory, detail route, featured slot, search) with zero further code changes needed.

**Existing file-transfer precedent already in the codebase:** `pubspec.yaml` already depends on `file_picker: ^12.0.0`, used by `DraftsBackupButton` / `DraftsFileTransfer` (`lib/features/cases/data/drafts_file_transfer.dart`) to let an editor "Guardar mi trabajo en un fichero" (download all drafts as a JSON file) and "Cargar trabajo desde un fichero" (load a picked file back in). Read the implementation: `FilePicker.saveFile(fileName:, bytes:, mimeType:)` — on Flutter Web this triggers a **browser download/save-as dialog**, not an arbitrary filesystem path write. The code comments this explicitly: "En web no hay rutas de fichero." **This means no in-app action, however built, can write directly back into the git checkout's `assets/data/cases.json`, even for local dev runs** — a browser (even a local `flutter run -d chrome` session) cannot target an arbitrary repo path via `file_picker`'s web implementation. A downloaded file still requires a manual move + `git add`/`git commit`.

### Affected Areas
- `lib/features/cases/application/case_exporter.dart` — current single-object export; would need a "merge into full catalog array" mode if Option A is chosen.
- `lib/features/cases/data/local_cases_repository.dart` / `cases_repository.dart` — confirmed read-only single source of truth; no write path exists.
- `lib/features/cases/presentation/intake/export_case_button.dart` — current clipboard-only single-case export UI.
- `lib/features/cases/presentation/intake/drafts_backup_button.dart` + `lib/features/cases/data/drafts_file_transfer.dart` — existing, working "download JSON as file" precedent (file_picker-based) that could be extended/reused instead of building new file-save plumbing.
- `assets/data/cases.json` — the manually-edited catalog array; single source of truth for map/directory/detail/search/featured.
- `openspec/specs/case-editorial-chapters/spec.md` (Requirement: Manual Publication Boundary) — current spec explicitly requires export to NOT auto-update the catalog; any automation beyond "easier export" would need to amend or supersede this requirement, not silently violate it.

### Approaches

1. **Option shape A — Reduce/eliminate the JSON-splice step, keep git-based manual publication.** Two concrete variants, both compatible with a static GitHub Pages host and the existing Manual Publication Boundary spirit (though the spec text itself would need updating to describe the new export shape):
   - **A1 (smallest change):** Extend the exporter/button so it can emit a ready-to-paste **array fragment** (or a full merged array, given the currently-loaded published catalog + the draft) instead of a bare object — still clipboard-based, still requires opening the file and pasting, but removes the "where exactly do I put the comma" error class.
   - **A2 (reuse existing file infra):** Add a "Download updated cases.json" action next to/inside `ExportCaseButton`, reusing the already-proven `DraftsFileTransfer`/`file_picker` pattern from `DraftsBackupButton`, that downloads the **full catalog array** (existing cases + the new/edited one, correctly merged, deduped by slug) as a ready-to-drop-in file. The maintainer still does: download → replace `assets/data/cases.json` → `git commit`. No hand-JSON-editing at all.
   - Pros: Low-to-medium effort, no backend, no credentials, stays inside the static-hosting model, directly reuses two patterns already proven in this codebase (`draftToCaseJson` schema fidelity + `file_picker` download flow).
   - Cons: Does not remove the "commit + deploy" step; "publish" still requires a human with repo write access to finish it. Requires amending the Manual Publication Boundary requirement's wording (not its intent) since it currently frames export narrowly.
   - Effort: Low (A1) to Medium (A2 — merge/dedupe logic, multi-draft handling, still needs strict TDD evidence).

2. **Option shape B — Real automation (commit-on-publish from inside the app).** E.g., calling the GitHub REST API directly from the browser to create a commit updating `assets/data/cases.json`, using an embedded token. Found **no evidence** this is wired or desired anywhere in the code, specs, or archived proposal — the archived proposal explicitly lists "Publication automation... manual clipboard → asset → commit → GitHub Pages" as a NON-GOAL, and nothing in `pubspec.yaml` or the codebase references GitHub's API, OAuth, or any credential storage.
   - Pros: Would be the only shape that removes the human commit step entirely.
   - Cons: Requires embedding write-scoped GitHub credentials in a public, statically-hosted web bundle protected only by the trivial hardcoded intake passphrase (`kIntakeSharedKey`) — a genuine credential-exposure risk, since any visitor who finds/guesses that passphrase (or reads it directly from the shipped JS/Wasm bundle, since it's a compile-time constant) would get it too. No backend exists to broker this safely. Directly contradicts the archived proposal's explicit non-goal and the still-current "Manual Publication Boundary" spec requirement — would need a deliberate, explicit decision to supersede that requirement, not just extend it.
   - Effort: High, and carries a real security decision the user should make explicitly, not one this exploration should default into.

Flagging Option B primarily to rule it out with evidence, per the task's own instruction, rather than to recommend it.

### Recommendation
Option shape A (specifically A2, reusing the existing `file_picker`/`DraftsFileTransfer` download pattern to emit a ready-to-drop-in full `cases.json`) most directly answers the user's actual complaint — the friction is the array-splice step, not the rendering pipeline, which is already complete and already renders chapters, photos, timeline, featured rank, and relevance rank correctly once a case is in the file. A1 is a smaller, even lower-risk first slice if the user wants to ship incrementally. Option B should only be pursued after an explicit, informed user decision about embedding write credentials in a public bundle — it is out of scope by default for a backend-less static site and would require rewriting the current Manual Publication Boundary spec requirement, not just adding to it.

### Risks
- The current `case-editorial-chapters` spec's "Manual Publication Boundary" requirement will need explicit amendment (via `sdd-propose`/`sdd-spec`) if any export-side automation ships — otherwise the change would silently contradict a still-current, shipped requirement.
- `published-case-directory` spec explicitly forbids using `featuredRank`/`relevanceRank` for directory ordering — any new UI (e.g., a "featured" section) must not repurpose directory ordering for that; it already has its own provider (`featuredCaseProvider`).
- `assets/data/cases.json` and two test files show as locally modified (uncommitted) at session start per git status — there may already be an in-progress manual paste in the working tree; worth checking before starting apply work so this change doesn't stomp on unrelated WIP.
- A2's "merge full catalog + dedupe by slug" logic touches the same collision-guard logic (`uniqueCaseSlug`/`caseSlug`) already covered by `test/case_exporter_test.dart` — reuse, don't reimplement, to avoid drift between single-case export and full-catalog export slug handling.
- No true "publish to production" is possible without a human finishing move+commit+push — a proposal that promises full automation would overpromise against this static-hosting, backend-less architecture.

### Ready for Proposal
Yes — the codebase evidence is thorough enough to write a proposal. Before `sdd-propose` runs, the user should make one explicit product decision: **A1 (clipboard array-fragment fix) vs. A2 (full downloadable ready-to-drop-in catalog file) vs. explicitly deferring/rejecting Option B (real git/GitHub automation) for now.** This exploration deliberately does not choose among A1/A2 — that's the user's call — but rules out defaulting into B without a separate, explicit security conversation.
